# Real-time latency and jitter under interference

_Generated by `scripts/make_realtime_report.py` from `results/realtime/runs/` (do not edit by hand)._

**Platform: AWS EC2 NVIDIA L4 VM (32 vCPU AMD EPYC 7R13), not an industrial edge device, not PREEMPT_RT, hypervisor noise present.** Kernel `6.1.158-178.288.amzn2023.x86_64` (`#1 SMP PREEMPT_DYNAMIC Mon Nov  3 18:38:36 UTC 2025`); preemption model: PREEMPT_DYNAMIC kernel, active mode (none) voluntary full. No `isolcpus`/`nohz_full`, IRQs not steered. Numbers are measured on this VM only and do not transfer to a Jetson/IPC target without re-measuring.

## What is measured

`cpp/bench/latency_bench` runs the BEVFusion TensorRT FP16 engine (`results/export/bevfusion_fp16.engine`, TensorRT 10.16) in a periodic loop at **30 Hz** (absolute `clock_nanosleep(CLOCK_MONOTONIC)` releases, deadline = period = 33.33 ms). One job = host staging copy of the 24.2 MB input frame (pageable -> pinned, stand-in for pre-processing; voxelisation and LSS indexing are not ported to C++), H2D copies, `enqueueV3`, D2H of all outputs (49.8 MB incl. the occupancy volume), stream synchronise.

* **e2e** = wake-up to outputs on the host; **response** = planned release to outputs on the host.
* **jitter** = wake lateness (actual wake - planned release); sd and max over all pooled iterations.
* **miss** = response > deadline. Overruns follow a frame-drop policy (stale releases skipped, counted).
* Each config: 3 repeats x 2000 measured iterations (100 warm-up iterations excluded); percentiles pooled over repeats (numpy linear = C++ rt_stats).
* p99 range = min..max of the per-repeat p99, to show run-to-run noise.

Interference generators: **idle**: no load besides the benchmark; **cpu**: 32 spinning threads (`cpu_hog --mode cpu`), one per vCPU; **membw**: 16 threads memcpy-ing 2x256 MiB buffers (`cpu_hog --mode membw`); **gpu**: second process free-running the same TensorRT FP16 engine back to back (GPU co-tenant); **gpuinproc**: synthetic FMA kernel (4640 x 256 threads, ~0.74 ms per launch) looping on a second CUDA stream inside the benchmark process; **gpuproc**: the same synthetic FMA kernel looping in a separate process (`gpu_hog`); **combined**: 16 cpu threads + 16 membw threads + the TensorRT co-tenant process.

Why `cpu__pin` hurt: confining only the hogs (taskset) to the other 30 CPUs leaves CPUs 15/31 as the only idle CPUs, so the scheduler migrates every other runnable task there. A separate diagnostic run (`ps -eLo psr` sampling, not part of the tables) showed s3fs mount daemons and other system.slice threads running on 15/31 next to the benchmark; the loop thread's involuntary context switches rose from 1588 to 9643 per run. Pinning only works together with SCHED_FIFO (`cpu__pin_fifo`) or real isolation of everything else (`cpu__pin_iso`, cgroup cpuset).

Memory bandwidth is not fixed by any CPU-side mitigation: under `membw__pin_fifo` the deadline tail is gone, but the host staging copy still takes 9.21 ms p50 vs 2.10 ms idle and e2e p50 stays at 26.78 ms vs 19.54 ms (shared DRAM / L3; would need memory-bandwidth throttling of the noisy neighbour (AMD PQoS / Intel MBA; this VM shows no rdt_a/mba CPU flags and no resctrl filesystem) or less host copying).

Under combined load the best configs still miss: `combined__all` 27 / 6000, `combined__all_iso` 77 / 6000 (p99 32.69 vs 33.43 ms); the remaining tail comes from the memory-bandwidth slowdown of the staging copy plus the GPU share the MPS-limited co-tenant still takes, which cpuset isolation does not address.

## Limitations

* Cloud VM (AWS EC2, NVIDIA L4, AMD EPYC 7R13): vCPUs are hypervisor threads, steal time and host interrupts are outside our control; not an embedded/edge device and not a PREEMPT_RT kernel. Absolute numbers and tails will differ on Jetson Orin or an industrial PC.
* No `isolcpus`, `nohz_full`, `rcu_nocbs` or IRQ affinity (would need a reboot with new kernel parameters); pinning uses taskset only, so kernel threads and IRQs can still run on the inference core.
* One input frame replayed every iteration (static shapes, so per-frame content does not change the work); pre-processing is a staging memcpy, not the real voxelisation/LSS indexing.
* CUDA stream priorities only act inside one CUDA context; they cannot prioritise against another process (that case is covered by MPS and co-tenant rate limiting instead). GPU time-slicing between processes without MPS is controlled by the driver and cannot be tuned here.
* MPS was started only for the `mps25` / `all` / `all_iso` configs; under MPS the benchmark itself is also an MPS client. With 25 % of the SMs (14 of 58) TensorRT warns that the co-tenant engine was built for 58 SMs and that deadlocks are possible; no deadlock occurred in these runs, but a production setup would build the co-tenant engine for its SM budget.
* The cpuset isolation is done at runtime with `systemctl set-property --runtime ... AllowedCPUs` (cgroup v2) and undone after the config; kernel threads and IRQs are not moved by it.
* 3 repeats per config: enough to see repeat-to-repeat spread, not enough for tight confidence intervals on p99.9 and max (pooled n per config is shown).
